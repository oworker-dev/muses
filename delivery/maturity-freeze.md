# SaaS Starter Maturity Freeze

This document records the maturity decision for the first general-purpose OWorker SaaS Starter baseline.

The freeze means the starter is mature enough to stop feature expansion and feed its verified standards back into Core Starter and Application Starter. It does not mean every future product requirement belongs in this starter.

## Decision

OWorker SaaS Starter is a mature release-candidate baseline when:

- source-package checks pass from the starter root;
- a clean project generated by `oworker starter create saas` passes the V1 release gate;
- Docker runtime health, integration health, smoke, ANSS conformance, and browser checks pass;
- public, account, billing, admin, health, support, and legal surfaces are neutral and replaceable;
- ANSS discovery, service map, OpenAPI, ACLIP CLI, MCP, Skills, and install manifests stay generated from one capability source;
- no development-only billing, auth, provider, or fallback path can grant production privileges;
- docs describe general starter standards and do not assume a product-specific SaaS business.

## Mature Baseline

The starter baseline includes:

- neutral public landing page with OWorker branding and CLI creation path;
- auth lifecycle with email/password, email verification, password reset, password change, verified email change, optional OAuth, and protected routes;
- account console for identity, avatar, security, connected accounts, settings, billing, and subscription state;
- site admin console for users, revenue, subscriptions, analytics, service health, audit logs, diagnostics, and provider status;
- Stripe-compatible checkout, portal, persisted subscription state, payment records, and idempotent webhook handling;
- S3-compatible object storage with presigned uploads and avatar storage;
- Resend-compatible transactional email templates with provider-neutral boundaries;
- first-party aggregate analytics without raw IP storage;
- PostgreSQL, Valkey, MinIO, BullMQ, worker, Hono API, MCP, CLI, and structured logs;
- production configuration doctor, smoke checks, E2E checks, and Docker scripts;
- ANSS v0.1 discovery and conformance loop.

## Freeze Rules

After this freeze:

- do not add new SaaS product modules to the default baseline;
- do not add team/workspace, CRM, project management, notifications, status page, AI workflow, knowledge base, or product-specific dashboard modules by default;
- only fix blockers found by the V1 release gate, browser QA, generated package regression, or security review;
- move reusable standards back into Core Starter and Application Starter instead of expanding SaaS Starter;
- publish product-specific variants as separate native starters after their own contracts and verification are coherent.

## Backport Scope

Core Starter should inherit standards, not runtime:

- stable OWorker project structure;
- `.oworker` control-plane semantics;
- `AGENTS.md`, `DESIGN.md`, `delivery/`, `interfaces/`, `integration/`, `ops/`, `src/`, and `tests/` boundary language;
- contract and consumer-agent description surfaces;
- verification expectations that do not assume a language, framework, database, UI, or Docker runtime.

Application Starter should inherit general application standards, not SaaS business:

- mainstream Next.js application structure;
- shadcn dashboard-quality UI baseline;
- theme, metadata, icon, responsive, and accessibility discipline;
- health endpoint and browser-visible app shell;
- minimal ANSS discovery for implemented application capabilities;
- package scripts, Docker workflow, smoke checks, and generated-package verification.

## Required Final Evidence

The maturity decision is complete only when:

1. `pnpm run check` passes from the SaaS Starter source package.
2. A clean generated SaaS project passes `pnpm run check`.
3. The generated project passes `pnpm run build`.
4. Docker starts through `pnpm run docker:up`.
5. `pnpm run smoke` passes against the generated Docker runtime.
6. ANSS conformance and Agent probe pass against the generated runtime.
7. Browser QA covers public, auth, account, billing, admin, health, settings, support, legal, mobile, light theme, and dark theme paths.
8. `oworker starter verify` passes against the generated project.

When these checks pass, SaaS Starter should be treated as stable enough for RC. Reusable standards should flow back into Core/Application; new product-specific modules should be handled as separate starters, extensions, or created-project work.

The Core/Application backport and family gate have been completed. Further work should focus on publishing mechanics, documentation, packaging safety, and optional extensions rather than expanding the default SaaS baseline.
