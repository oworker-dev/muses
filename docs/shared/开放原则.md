# 开放原则

> 当前公开快照尚未写入 `LICENSE`，因此“完全开源”是已批准的项目方向，而不是已经生效的法律许可。许可证选择和落地由 APCC 任务 `select-open-source-license` 管理；在 `LICENSE` 发布前，不得对外宣称 Muses 已完成开源发布。

## 1. 基本立场

Muses 默认完全透明开源，并以 Build in Public 作为长期开发模式。我们不把代码保密、专有文件格式或用户迁移成本当作主要壁垒；长期竞争力来自更深的用户理解、更好的体验判断、真实工作流、开放协议、社区信任和持续交付能力。

> 产品建设透明，用户数据私密；能力边界开放，安全责任明确。

开放不是营销活动，而是可以被用户验证的产品性质：用户能够检查系统如何工作、选择如何运行、带走自己的数据和成果，并参与路线与改进。

## 2. 默认公开的内容

- 核心产品、通用内核、官方客户端、协议、数据格式和迁移工具源码。
- 架构文档、APCC 长期目标、公开计划、重要决策及其理由。
- Issue、里程碑、变更记录、贡献流程和兼容政策。
- 模型与供应商适配接口、能力评测方法和已知限制。
- 定价原则、可公开的成本结构和服务边界。
- 经匿名、聚合和隐私审查后的价值指标、实验结论和失败复盘。
- 安全政策、负责任披露流程、许可证和治理规则。

“默认公开”不意味着未经审查自动发布；每项公开内容仍需满足隐私、安全、许可与诚实表达要求。

## 3. 永不因 Build in Public 而公开的内容

- 用户私有素材、提示、项目、客户文件、未发布作品和业务数据。
- API Key、OAuth Secret、签名密钥、基础设施凭证和私有环境配置。
- 可识别个人的遥测、通信、支付或使用记录，除非获得明确授权并满足合规要求。
- 能直接帮助绕过安全控制的未修复利用细节。
- 第三方合同、模型、数据集、字体、媒体或商业内容中无权公开的部分。
- 贡献者或员工依法应受保护的个人信息。

用户内容默认不用于模型训练。若未来提供可选数据贡献计划，必须独立、明确、可撤回、可审计，且不与基本服务捆绑。

## 4. 用户自由

开放产品至少保障：

- **运行自由**：用户可以在许可证范围内自托管和修改系统。
- **数据自由**：可以导出结构化项目、资产、版本、工作流和来源记录。
- **模型自由**：可以使用官方路由、兼容供应商或自有凭证，具体受安全和能力兼容约束。
- **部署自由**：官方云是便利选项，不是使用核心格式和能力的唯一途径。
- **迁移自由**：公开 Schema、版本策略和迁移工具，不通过格式陷阱维持留存。
- **创作自由**：在合法、安全和第三方许可范围内，用户决定如何使用自己的成果。

自由不等于平台免除安全、法律和社区责任；内容安全规则、资源配额和外部发布权限必须透明、可申诉并尽量可配置。

## 5. Build in Public 工作方式

- 在开始高影响工作前公开问题、假设、范围和成功/停止标准。
- 用 APCC Decision 记录 Goal、范围、架构、政策和版本变化。
- 公开小步、可运行的进展，而不是只展示最终宣传成果。
- 同时公开失败、取舍、成本与已知限制，避免只选择性展示成功。
- 优先使用公共 Issue/Discussion 接收反馈；涉及隐私或安全时提供私密通道。
- 路线图表达当前判断而非不可变承诺，并标注证据强度。
- 公开指标服务学习，不制造虚荣数字或泄漏个体行为。

## 6. 贡献与治理原则

- 贡献规则、行为准则、审查标准、维护者职责和决策升级路径必须公开。
- 外部贡献与内部代码使用相同质量、安全、兼容和价值门。
- 核心协议变化需要公开提案、迁移方案和 APCC/架构决策。
- 维护者可以因安全、法律、隐私、可维护性或产品方向拒绝贡献，并说明可公开理由。
- 社区影响力来自持续贡献与责任，不通过私有关系产生隐藏特权。
- 商标、项目身份和官方服务认证可以独立治理，以防止混淆和恶意分发。

## 7. 许可证策略

项目承诺采用符合上述自由目标的开源许可证，但在评估以下问题前不仓促写入最终许可证：

- 是否要求提供网络服务的修改者公开对应源码。
- 插件、SDK、模型适配器和企业集成的兼容性。
- 贡献者许可、专利保护与第三方依赖兼容性。
- 自托管自由与官方托管服务可持续性的平衡。
- 社区与商业用户能否清楚理解义务。

AGPLv3 是优先评估候选，不是本文件直接作出的最终法律决定。正式许可证必须通过独立 APCC `policy` 决策，并在必要时获得专业法律审查。确定之前不得对外宣称某一具体许可证已经生效。

## 8. 开源商业模式

官方商业价值来自降低用户运营复杂度：托管、算力、存储、可靠性、协作、模型路由、合规、支持和专业工作流。用户付费购买更好的服务结果，不购买解除人为限制的权限。

不得作为主要商业手段：扣留数据、禁用标准导出、隐藏成本、制造无法迁移的格式、故意削弱自托管版本、将安全修复长期只提供给付费用户。

允许建立清晰的官方云、企业支持、托管基础设施、市场服务和认证商业边界，只要核心自由、公开契约和用户数据权利不被破坏。

## 9. 开放质量门

每个稳定版本发布前应验证：

- 新核心功能的源码、契约、迁移和文档是否同步公开。
- 自托管路径是否仍可运行，官方云专有依赖是否有清晰边界。
- 用户能否导出新增对象及其来源和版本。
- 路线、已知限制、安全与许可说明是否诚实更新。
- 是否意外提交密钥、个人数据、客户内容或受限材料。
- 外部贡献者能否从公开资料复现开发、测试和决策背景。

开放性退化属于产品回归，而不是文档瑕疵。
