# MVP 交付路线

> **归档路线说明**：本文记录 APCC `0.4.0-mvp-route` 时的 PPT 优先纵向切片和 25–37 日估算，不是当前任务队列。APCC 决策 `decision-5` 已将执行顺序调整为[用户成果驱动交付](用户成果驱动交付计划.md)：先验证用户友好的真实首图，随后用一个真实 PPT 任务逐项拉动缺口，不等待预设的 Platform Core 或 Agent 层全部完成。本文中的真实交付价值门、场景边界和削减原则仍可作为 PPT Gate 的历史输入；固定切片、日期估算和“真实 PPT 样本先冻结全部首批契约”的规则均不再生效。

## 1. 交付目标

首个 MVP 不是“功能很多的设计平台”，而是一条可用于真实 PPT 定制业务的最小生产闭环：

```text
Brief 与输入材料
→ Agent 生成可审阅的提纲和页面草稿
→ 用户在页面画布中局部编辑
→ UI、Agent 或固定生产配方调用同一个图像能力
→ 自动保存、恢复并保留任务、成本与来源
→ 导出可继续编辑的 PPTX 与结构化 Muses 项目
→ 在真实交付中与旧工作流对照验证
```

MVP 同时验证两个命题：

1. CreativeDocument、Command、Revision、Asset、Provenance、Job、Capability 与受控 Agent 等通用模块可以独立运行、通过公共契约连接并在产品中复用。
2. 这些模块能改善一项真实 PPT 商业材料任务，而不以扁平化结果、供应商锁定或不可解释自动化换取表面速度。

## 2. 为什么首个场景选择 PPT

PPT 定制来自创始人的真实业务，能够立即提供 Brief、输入材料、成品、修改记录、客户标准、时间和成本证据。它同时覆盖结构化文档、页面画布、文本、图像、基础形状、资产、版本、Agent、固定流程和可编辑导出，但暂时不要求视频时间线、音频同步和渲染集群，因此比 AI 短剧更适合做首个低风险贯穿切片。

PPT 不是内核类型。页面、母版和 PPTX 映射属于演示能力或场景层；通用内核不得出现 `pptProject`、`slideJob` 或客户行业特例。AI 短剧是 MVP 后的第二场景，用于检验共享内核是否真的能跨场景复用，并扩展时间线、视频、配音、音效和音乐专业语义。

## 3. 双轨推进

### Track A：真实价值证据

- 产品负责人提供一个可脱敏的真实 PPT 验收样本和旧流程基线。
- 开发中持续记录工具切换、人工搬运、首稿时间、总交付时间、返工、成本、可编辑性和客户采用结果。
- MVP 完成后至少观察一名外部同类用户无引导完成核心链路。
- 开源许可证和外部需求验证并行推进，但除真实 PPT 样本外，不把整个 Value Foundation 变成实现前的串行等待队列。

### Track B：通用能力贯穿切片

- 每个切片同时交付可独立运行的内核 Harness 和一段真实产品链路。
- 场景只能通过公开 Query、Command、Capability、Job、Asset 与导出端口组合能力。
- 每个 Gate 结束时产生可运行证据、已知限制和继续、削减或停止决定，不以代码量或抽象数量判断进度。

真实 PPT 样本是冻结首批契约的硬门；外部访谈、完整许可证治理和第二场景不是首个代码 Spike 的前置条件。

## 4. 通用模块成熟度

| 等级 | 含义 | 必要证据 |
| --- | --- | --- |
| `R0 实验` | 只用于回答一个高风险技术问题 | 可运行 Spike、结论、淘汰理由和未决风险 |
| `R1 独立可用` | 模块脱离完整产品也能运行 | 公开输入输出、Harness、确定性测试、故障语义和无隐式场景依赖 |
| `R2 产品可复用` | 模块已通过统一契约进入真实产品闭环 | 至少两个真实调用入口、一个真实适配器、契约测试、观测/成本/安全边界和真实 PPT 使用证据 |
| `R3 跨场景内核` | 模块在差异明显的第二场景中无需场景特例复用 | PPT 与 AI 短剧共同使用、迁移与兼容证据、稳定责任和维护承诺 |

首个 MVP 的目标是让首批通用模块达到 `R2`，而不是提前宣称它们是稳定平台内核。只有第二场景通过后才能升级到 `R3`。固定 PPT 生产配方可以作为第三调用入口，但它不等于通用工作流编辑器已经完成。

## 5. MVP 必须包含

### 通用能力

- CreativeDocument：版本化节点、页面扩展、稳定标识、资产引用和结构化导出。
- Command 与 Revision：校验、基线修订、幂等、撤销/重做、自动保存和恢复。
- 页面画布：页面画板、文本、图片、基础形状、选择、变换、层级、缩放和键盘操作。
- Asset 与 Provenance：上传、派生关系、元数据、授权访问、输入输出、供应商、参数和成本关联。
- Job 与 Capability：版本化 Manifest、类型化输入输出、进度、取消、受限重试、幂等提交和结构化错误。
- 受控 Agent：读取 Brief、项目和选择上下文，只通过公共端口生成大纲、页面草稿和局部修改。
- 固定生产配方：代码定义且版本化的 Brief、提纲、页面、图像处理、人工审阅和导出步骤。

### 场景闭环

- 创建一个 PPT 商业材料项目并导入 Brief、文本和图片材料。
- 生成并人工确认提纲和页面草稿。
- 在画布上直接修改核心文本、图片、位置、尺寸和层级。
- 根据真实样本选择一个图像生成或处理能力，由模拟与真实适配器共同验证。
- 刷新或短暂断线后恢复已确认内容，失败不能静默丢失状态。
- 导出核心文本、图片和基础形状仍可编辑的 PPTX，并输出明确兼容性报告。
- 导出带 Schema 版本和资产引用的 Muses 结构化项目，不把 PPTX 作为唯一权威格式。

## 6. 明确不进入首个 MVP

- 多人实时协作、CRDT/OT 和离线合并。
- 通用 DAG 工作流编辑器、工作流市场和复杂循环/并行编排。
- 视频时间线、音频、配音、音效、音乐和 AI 短剧完整链路。
- 完整 PPTX 往返保真、动画、宏、所有图表类型和所有第三方字体兼容。
- 完整品牌管理系统、模板市场、社媒发布、电商套件和插件生态。
- 多模型自动路由、复杂模型评估和无人监督的自主 Agent。
- 移动端、桌面端和企业级多人治理；现有租户、权限、审计基础仍必须被正确使用。

被排除项可以保留契约扩展点，不得提前实现通用框架。

## 7. 关键路径与退出门

以下时间是单一专注交付流的规划预算，不是发布日期承诺。每个 Gate 到期必须展示可运行结果；未完成时优先削减范围，不自动延长。

### Gate 0：验收样本与技术去险，3–5 个工程日

交付：

- 一个可脱敏真实 PPT 任务包及旧流程基线。
- 可编辑 PPTX 路线 Spike，验证页面、文本、图片、基础形状、字体和坐标映射。
- CreativeDocument、Command、Revision 到页面画布投影 Spike。
- MVP 技术需求/体验约束矩阵和首批最小 Schema 草案。

退出条件：可说明什么可以结构化保存、什么可以可编辑导出、什么会有损；选定画布与 PPTX 路线；冻结首批契约时不包含供应商 SDK 或 PPT 业务类型。若真实样本未提供，不冻结契约。

### Slice 1：文档、命令与页面画布，7–10 个工程日

交付：

- 文档、命令和修订内核的内存实现、契约测试与迁移样例。
- 页面画布最小编辑器。
- PostgreSQL 持久化、自动保存、刷新恢复和结构化项目导出。

退出条件：内核达到 `R1`；同一 Command 可由测试 Harness 和 UI 执行；已确认修改刷新后不丢失；撤销/重做和过期基线产生明确结果。

### Slice 2：资产、Job 与首个图像能力，5–7 个工程日

交付：

- 资产/来源和 Job/Capability 内核的内存实现与真实适配器。
- 模拟供应商和一个真实图像供应商共享契约测试。
- UI 调用能力并将派生资产通过 Command 放回页面。

退出条件：能力可独立调用；上传、进度、取消、失败、重试和重复提交可观察；结果拥有来源与成本；失败不留下悬空权威状态。

### Slice 3：Agent、固定配方与可编辑 PPTX，7–10 个工程日

交付：

- 受控 Agent 生成提纲、页面草稿和选择范围内的局部修改。
- 固定 PPT 生产配方复用相同 Capability、Job、Asset 与 Command。
- 可编辑 PPTX 导出、兼容性报告和端到端验收自动化。

退出条件：UI、Agent 和固定配方不复制核心能力逻辑；Agent 没有数据库写旁路；用户能检查、拒绝和撤销关键修改；验收样本能完成 Brief 到可编辑 PPTX 全链路。

### MVP Gate：真实交付，3–5 个工程日

交付：

- 至少一次真实 PPT 定制对照交付。
- 通用模块 `R1/R2` 计分卡和未通过项。
- 一名外部同类用户的无引导观察记录。
- 继续、修订、删除或停止的正式决定。

退出条件：真实成果被导出并进入交付或使用；相对旧基线至少改善速度、人工搬运、返工、成本或控制中的一项，且可编辑性、数据自由、可靠性和安全护栏没有倒退。没有证据的模块不得因“未来会用”继续扩张。

首个 MVP 的总规划预算约为 25–37 个专注工程日，即单一交付流约 5–7 周。准备样本、技术 Spike、视觉验收材料和真实交付可以有限并行；并行不能绕过 Gate 依赖。

## 8. 范围削减顺序

当 Gate 超时或风险上升时，按以下顺序削减，不牺牲权威状态、可恢复性和可编辑交付：

1. 删除额外模型、额外图像能力和视觉样式数量，只保留一个真实适配器。
2. 删除通用工作流 UI，只保留代码定义的固定生产配方。
3. 限制 PPTX 支持到文本、图片和基础形状，并明确报告不支持特性。
4. 限制 Agent 到提纲、页面草稿和选择范围内修改，不做全自主交付。
5. 限制导入格式和模板数量，不删除结构化项目导出。
6. 推迟外部用户扩量，但不取消首个真实对照交付。

不可削减：租户授权、命令边界、保存恢复、幂等提交、来源记录、成本可见、可编辑 PPTX 核心内容和结构化项目导出。

## 9. 首个验收样本需要什么

产品负责人应提供一个目录或受控共享位置，至少包含：

- 原始 Brief 和最终用途。
- 可公开或可脱敏的输入文本、图片、数据和品牌参考。
- 现有成品或可比较的目标样例。
- 当前使用的工具与逐步过程。
- 可获得的耗时、外部成本、返工轮次和文件搬运次数。
- 客户或交付方判定“可用”的标准。
- 哪些内容必须在 PPTX 中继续编辑，哪些可以有损降级。
- 不能进入代码库、日志、模型或公开文档的隐私与授权边界。

未知数据保持 `unknown`。不得为了启动开发而编造基线，也不要求先提供客户身份或敏感原始材料。

## 10. MVP 后路线

MVP 通过后先做一次稳定性与删除审查，再进入 AI 短剧第二场景。第二场景优先复用已有 Project、Document、Command、Asset、Job、Capability、Agent 与 Provenance；新增镜头、时间线、视频、配音、音效和音乐专业扩展。若共享内核需要 PPT 特例才能工作，应先修正边界，不把特例复制到第二场景。

只有通过差异明显的第二场景、兼容迁移和故障测试后，相关模块才能从 `R2 产品可复用` 升级为 `R3 跨场景内核`。
