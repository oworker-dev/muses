# 内核验收路线

## 1. 目的

平台优先不等于先造一个庞大框架。每个内核都必须以可运行证据证明抽象成立，业务场景只作为验收夹具，不进入内核代码或协议。

技术成熟度仍遵循“直接操作证据 → 单 Agent 复用 → 多 Agent 编排”的依赖方向，但产品交付不再等待整层完成。每轮先定义用户可见成果，用当前产品运行并记录缺口，再只补最小阻断。场景既是价值验证，也是发现通用能力边界的输入；它不能把 PPT、行业或供应商特例写进内核。

## 2. 三层验收门

### Gate A：独立运行

模块拥有明确输入输出、最小 Playground 或测试 Harness、无隐式全局依赖，并能在不启动完整产品场景的条件下完成核心行为。失败、空输入、取消和版本不兼容都有可观察结果。

### Gate B：协议复用

模块只能通过公开契约被调用。至少两个不同调用方使用相同接口，契约测试对内存实现和真实适配器同时运行。替换供应商或 UI 不改变上游领域模型。

### Gate C：跨模块与入口组合

模块至少接入两个真实调用入口，并通过相邻内核形成可运行产品链路；输出进入共享 Artifact/Asset/Job/Command 体系，具备来源、权限、幂等、取消或撤销等适用语义。首个 MVP 以 UI、Agent 和代码定义的固定配方作为复用证据；固定配方不等于通用工作流运行时已经成熟。

通过 Gate C 和首个场景 Gate V 后可称为“产品可复用模块”；只有在差异明显的第二场景中无需场景特例复用后，才可称为“跨场景平台内核”。

### Gate V：用户价值成立

模块必须进入至少一个真实交付并改善预先声明的价值指标，同时不突破成本、自由、可靠性和安全护栏。Gate V 可以与 Gate A–C 并行收集证据，但不能被技术测试替代。没有价值改善的通用模块不得因“未来可能需要”无限打磨。

## 3. 当前建设阶段

详细技术边界、Spike 夹具和交付顺序以 [平台核心 Alpha 路线](平台核心Alpha路线.md)为准。

### Gate 0：最小技术基线与核心契约

用场景无关的两层画布夹具验证工作流无限画布、DesignDocument 聚焦编辑、命令驱动、序列化、恢复、性能与可访问性。只在采用/淘汰证据形成后冻结库无关的最小 Schema 与包边界。

### Platform Core Alpha

工作流图、DesignDocument、Asset/Provenance、Job/Capability 和媒体能力是缺口池，不是串行组件队列。当前先让人通过 `Start → image.generate → End` 获得一张真实图片；只实现该任务暴露的最小能力，确保核心不是依赖 Agent 才能运行的演示。

### Agent Core Alpha

当首图或 PPT 等真实任务证明直接 Capability 与人工工作流不足时，才接入通用 Agent Runtime 和单 Agent。Agent 只能通过 Query、Command 与 Capability 重现已经直接证明的操作，并通过预算、确认、取消、恢复和撤销验收。

### Agent Orchestration

单 Agent 可靠后，再交付 MusesAgent、领域 Agent 配置、委托协议与 Runtime 管理的执行型 SubAgents。固定组织层级不进入通用内核。

### Scenario MVP

首图 Gate 通过后立即用 MusesPPT 真实任务运行当前平台，由实际首个阻断决定是否拉动文本、Agent、PresentationDocument、设计或 PPTX。AI 短剧是第二场景并扩展真实缺失的时间线、视频、配音、音效和音乐。场景不得反向定义平台核心。

## 4. 首个平台核心组合证明

以下链路保留为组合成熟度证明，不是首图默认路径，也不是开始 PPT 价值验证的前置条件：

```text
输入图片节点
  → 调用图像生成或处理 Capability
  → Job 产生带来源和成本的结果分支
  → 用户比较并选择一个结果
  → Command 将结果送入 DesignDocument 节点
  → 用户进入专业画布局部编辑
  → 返回外层继续连接并保存恢复
```

首图 Gate 先证明用户能够获得真实结果。Platform Core Gate 再证明被实际拉取的 UI 与 Harness 共享命令和能力语义；需要 Agent 时，Agent Core Gate 证明单 Agent 通过相同端口完成已验证操作；PPT 与 AI 短剧继续提供价值和跨场景复用证据。每一层都不得复制业务逻辑或绕过权威状态。

## 5. 每个内核的交付物

- 一页职责、非职责、权威数据与依赖说明。
- 版本化类型/Schema 和兼容策略。
- 参考内存实现或测试替身。
- 至少一个真实适配器。
- 契约、状态机、迁移、安全与故障测试。
- 最小 Playground/Harness。
- 指标、日志、追踪与成本字段。
- 已知限制和下一次重审条件。

## 6. 质量计分卡

| 维度 | 必须回答的问题 |
| --- | --- |
| 独立性 | 是否能脱离具体场景运行和验证？ |
| 复用性 | 是否至少有两个真实调用方且没有复制逻辑？ |
| 组合性 | 是否通过标准标识、Schema、Job、Command 或事件连接？ |
| 可恢复性 | 失败、取消、重试、重复投递和断线后会怎样？ |
| 可演进性 | 旧数据、旧工作流和旧调用方如何兼容？ |
| 安全性 | 租户、权限、敏感数据和外部副作用在哪里校验？ |
| 可解释性 | 输入、模型、参数、操作者、成本和产物能否关联？ |
| 可替换性 | 更换供应商或实现是否不改变上游领域语义？ |
| 可运营性 | 是否有 SLO、指标、诊断、配额和成本归因？ |
| 用户价值 | 是否改善真实任务的速度、质量、控制、自由度或成功交付成本？ |
| 开放自由 | 是否可由公开源码验证，并支持结构化导出、迁移或自托管边界？ |

任何一项没有明确答案，模块都不能进入稳定内核层。

## 7. 场景夹具规则

AI 短剧、PPT 定制、电商、短视频和品牌可以用于发现需求与验收组合价值，但必须遵守：

- 场景类型只存在于场景层或配置中。
- 场景不得直接访问内核数据库表或供应商 SDK。
- 被两个场景重复需要的行为先判断是否属于已有 Capability，而不是立即新增“通用”抽象。
- 只有经过至少两个差异明显的调用方验证后，场景抽象才提升为平台契约。
- 场景交付压力不能跳过来源、权限、幂等、迁移和租户隔离。
- 场景实验必须在开发前记录基线指标和停止阈值，开发后记录真实交付结果。
- 创始人业务是首批证据但不是永久唯一证据；必须持续邀请外部目标用户复现。

## 8. APCC 管理方式

当前以 `platform-core-alpha/first-image-value-gate` 为唯一工程关键路径；首图通过后进入 `scenario-mvp/muses-ppt-mvp` 的真实任务走查。`agent-core-alpha` 仅在真实任务暴露非确定性规划或工具循环缺口时拉取，`agent-orchestration-alpha` 必须晚于单 Agent 可靠闭环。真实价值证据与开放治理保持并行计划。每个 Gate 建立可验收 Task；范围、架构、开放政策与许可证变化记录 Decision；稳定里程碑记录 Version；实现证据、价值实验和风险写入 `delivery/`。计划状态以任务自动推导，不在文档中手工维护百分比。
